# WEEKLY SIGNAL 주간 제작 절차

이 문서는 한 호를 조사·작성·편집·검수·발행하는 실행 순서를 규정한다. GitHub Actions는 사용하지 않는다. 최종 통과 여부는 자동 검사보다 직접 편집 검수와 사용자 승인으로 결정한다.

## 1. 시작 전에 읽을 현행 기준

새 회차를 시작할 때 다음 문서를 읽는다.

1. `editorial/EDITORIAL_STANDARD.md`
2. `editorial/ISSUE_QUALITY_GATE.md`
3. `editorial/SECTION_AND_DEEP_DIVE_STANDARD.md`
4. `editorial/HEADLINE_AND_EDITORS_PICK_STANDARD.md`
5. `editorial/VOICE_AND_TONE.md`
6. `editorial/SOURCE_POLICY.md`
7. `editorial/IMAGE_DIRECTION.md`
8. `editorial/LAYOUT_SYSTEM.md`
9. `editorial/PUBLISHING_PIPELINE.md`
10. `templates/TEMPLATE_CONTRACT.md`
11. `templates/NAVIGATION_CONTRACT.md`

HTML 제작 단계에서 `templates/ISSUE_TEMPLATE.html`을 시작 셸로 사용한다.

## 2. 작업 브랜치

- 새 회차는 최신 `main`에서 `issue/YYYY-MM-DD` 브랜치를 만들어 작업한다.
- 작업 브랜치는 미완성 회차를 공개 `main`과 분리하기 위한 용도다.
- 조사 메모·이미지 후보·중간 HTML은 작업 브랜치에만 둔다.
- 사용자 승인 전에는 새 회차를 `main`에 반영하지 않는다.

## 3. 기본 구성

별도 지시가 없으면 다음 구성을 목표로 한다.

- Cover Story 1편
- Economy 일반 기사 1편
- Politics 일반 기사 1편
- Society 일반 기사 1편
- Tech 일반 기사 1편
- DEEP DIVE 1~2편
- LIFE SCENE 1편
- EDITOR'S PICK 1편
- Sources

Cover Story가 특정 분야를 다뤄도 해당 분야 일반 기사를 생략하지 않는다. 기사 후보가 부족하면 리서치를 계속한다.

## 4. 리서치

1. 대상 주간의 이슈를 분야별로 수집한다.
2. 각 기본 분야에서 후보를 최소 2개 이상 검토한다.
3. 핵심 사실·수치·법적 상태·계약·시행 여부를 1차 자료로 확인한다.
4. 발표·검토·계획·MOU·계약·시행·집행·성과·전망을 구분한다.
5. 법령·결정문·예산·통계·담당기관 자료와 신뢰할 수 있는 반론을 함께 조사한다.
6. 근거가 약하거나 서로 중복되는 후보를 버린다.
7. Cover Story와 분야별 기사 간 주제가 과도하게 겹치지 않는지 확인한다.

다음이 충족되기 전에는 집필하지 않는다.

- Cover Story와 4개 분야 기사 후보가 모두 선정됨
- 각 기사에 사건·수치·절차·영향·반론 근거가 있음
- 주요 기사에 독립적인 1차 자료가 충분함

## 5. 일반 기사 작성

1. Cover Story와 Economy·Politics·Society·Tech 일반 기사를 모두 작성한다.
2. 독자가 핵심 용어를 처음 접한다고 가정한다.
3. 핵심 사실, 오해 교정, 정의, 배경, 작동 구조, 적용 범위, 실제 영향, 상태 구분, 반론과 후속 판단 기준을 본문 안에서 완결한다.
4. 공식 문서 순서가 아니라 독자의 질문 순서로 재구성한다.
5. 기사마다 독립적으로 사실 검증하고 문장을 개정한다.
6. 모든 기사가 동일한 소제목 수와 문단 리듬을 갖지 않게 한다.
7. 본문이 디자인·카드·이미지 없이도 충분히 읽힐 때만 다음 단계로 간다.

이 단계에서는 DEEP DIVE, LIFE SCENE, EDITOR'S PICK, 이미지와 HTML을 먼저 만들지 않는다.

## 6. DEEP DIVE

1. 완성된 일반 기사 전체를 읽고 심화가 필요한 기사만 고른다.
2. 일반 기사가 이미 답한 질문을 적는다.
3. DEEP DIVE가 새로 답할 단 하나의 질문을 확정한다.
4. 새 핵심 주장 최소 3개와 새 독립 출처 최소 2개를 확보한다.
5. 쟁점 대립·정책 필요성·구조 해부·결과 시나리오·역사 비교 중 적합한 형식을 선택한다.
6. 같은 정의·원인·경로·결론을 반복하지 않는다.

차이를 만들 수 없으면 DEEP DIVE를 억지로 붙이지 않고 다른 질문이나 다른 기사를 선택한다.

## 7. LIFE SCENE

1. 일반 기사와 DEEP DIVE가 완성된 뒤 주제를 고른다.
2. 개인의 선택이나 주의로 해결되는 문제가 아니라 외부 제도·기관·서비스의 생활 문제인지 확인한다.
3. 평범한 일상, 현실적 가상 인물, 제한된 정보, 기대와 실제의 차이를 중심으로 쓴다.
4. 대기·이동·비용·정보 부족·일정 변경·돌봄·책임 공백 중 최소 세 가지가 자연스럽게 누적되게 한다.
5. 제목과 부제는 생활 장면을 중심으로 쓴다.
6. 마지막 `SCENARIO NOTE`에서만 정책과 기사 연결을 설명한다.
7. 개인 투자·소비·자기관리 조언으로 끝내지 않는다.

## 8. EDITOR'S PICK

전체 원고가 완성된 뒤 마지막 원고로 쓴다.

- 실제로 판단이 바뀐 한 지점 또는 오래 남은 한 사실을 중심축으로 고른다.
- 모든 기사를 언급하려 하지 않는다.
- 기사명보다 편집 과정의 판단과 인상을 쓴다.
- 한 문단에 기사 하나씩 배치하지 않는다.

## 9. 지면 설계

1. DATA와 WATCH는 새 정보가 있을 때만 만든다.
2. 대표 기사의 표지 주제를 확정한다.
3. 기사마다 내용에 맞는 지면 조합을 선택한다.
4. 한 호에 최소 세 가지 이상의 기사 레이아웃 리듬을 만든다.
5. 템플릿의 동일 구조를 모든 기사에 복제하지 않는다.
6. 장식 모듈은 본문을 반복하지 않고 새로운 정보나 읽기 전환을 제공해야 한다.

## 10. 이미지 제작

1. 모든 주요 이미지를 실제 이미지 생성 모델로 새로 만든다.
2. 표지·Cover Story·각 분야 기사·DEEP DIVE·LIFE SCENE에 서로 다른 역할과 구도를 부여한다.
3. Cover 장변 1800px 이상, 나머지 주요 이미지 장변 1600px 이상을 사용한다.
4. 벡터·SVG·플랫·아이콘·아이소메트릭 이미지를 사용하지 않는다.
5. 외부 이미지 URL을 직접 연결하지 않고 회차의 `assets/`에 저장한다.
6. 각 파일을 실제로 열어 얼굴·손·장비·문자 오류와 디테일을 확인한다.
7. 데스크톱과 모바일 크롭을 확인한다.

이미지에 실패하면 임시 그래픽으로 대체하지 않고 다시 생성한다.

## 11. HTML 제작

1. `ISSUE_TEMPLATE.html`을 시작점으로 사용하되 그대로 복제한 결과를 완성본으로 보지 않는다.
2. 완성된 본문·CSS·최소 JavaScript를 회차별 `index.html` 하나에 넣는다.
3. DEEP DIVE는 관련 일반 기사 바로 뒤에 둔다.
4. 목차·내비게이션·DOM 순서를 일치시킨다.
5. 기본 분야 기사 누락을 다시 확인한다.
6. 미사용 클래스, 숨겨진 모듈과 임시 주석을 삭제한다.
7. 회차 루트에는 `index.html`과 `assets/`만 둔다.

## 12. 실제 화면 검수

다음 화면을 실제 렌더링하거나 캡처해 확인한다.

- 1440px 이상
- 1366px
- 1024px
- 390px

확인 항목:

- Cover 제목 안전영역과 이미지 선명도
- 기본 구성과 Contents 일치
- 기사별 시각적 차이
- DEEP DIVE 중복 여부
- LIFE SCENE 서사 흐름
- 이미지 디테일과 크롭
- 표·카드·제목 오버플로
- 링크와 상대경로

HTML 코드만 읽고 화면 검수를 통과했다고 기록하지 않는다.

## 13. 보조 구조 검사

필요하면 직접 실행한다.

```bash
python -m pip install -r requirements-tools.txt
python tools/validate_repository.py
```

이 검사는 외부 이미지, 분할 HTML, 누락 파일과 잘못된 링크 같은 기술적 실수를 찾는 용도다. 기사 깊이, 이미지 미감과 지면 완성도를 판정하지 않는다.

## 14. 비교 검수

제1호와 새 회차를 나란히 비교한다.

- 한 호의 밀도가 지나치게 낮아지지 않았는가
- 섹션 전환과 기사별 리듬이 있는가
- 이미지 품질이 떨어지지 않는가
- 긴 블로그 문서가 아니라 매거진으로 보이는가

제1호 코드는 복제하지 않는다. 품질이 낮으면 발행하지 않는다.

## 15. 사용자 승인과 발행

1. 완성 화면과 주요 이미지를 사용자에게 보여준다.
2. 지적된 문제를 수정하고 다시 검수한다.
3. 명시적 승인 후에만 완성 회차를 `main`에 반영한다.
4. `ISSUE_HISTORY.md`, `issues.json`, `archive/index.html`, `latest.json`은 마지막에 갱신한다.
5. GitHub Pages는 `main` 루트의 정적 파일을 사용한다.

GitHub Actions, 자동 배포와 자동 병합은 사용하지 않는다.

## 16. 실패 처리

- 실패본을 `main/archive/`에 남기지 않는다.
- 작업 브랜치에서 원고·이미지·HTML을 다시 만든다.
- 기술 조건만 형식적으로 맞추는 우회 수정을 하지 않는다.
- 외부 이미지가 준비되지 않았거나 실제 렌더링을 확인하지 못한 상태는 발행 불가다.
