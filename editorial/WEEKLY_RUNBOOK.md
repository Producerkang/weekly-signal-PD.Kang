# WEEKLY SIGNAL Weekly Runbook

이 문서는 매주 발행 작업의 실행 순서, 단계별 산출물과 중단 조건을 규정한다. 기준의 상세 정의를 반복하지 않고 해당 전문 문서를 참조한다.

## 0. 시작 전 문서와 권한

다음 문서를 순서대로 읽는다.

1. `editorial/EDITORIAL_STANDARD.md`
2. `editorial/VOICE_AND_TONE.md`
3. `editorial/SOURCE_POLICY.md`
4. `editorial/IMAGE_DIRECTION.md`
5. `editorial/LAYOUT_SYSTEM.md`
6. `templates/TEMPLATE_CONTRACT.md`
7. `editorial/ISSUE_HISTORY.md`
8. 이 문서

파일명·경로·읽기 순서를 바꾸면 기존 예약 작업도 함께 갱신한다. 경로와 순서를 유지하면 예약 작업을 별도로 수정하지 않는다.

충돌 시 규칙 우선순위는 `EDITORIAL_STANDARD.md`의 문서 권한 절을 따른다.

## 1. 보안·저장소 사전 점검

작업 대상은 `main`의 최신 상태다.

시작 전 확인:

- 작업 브랜치와 최신 커밋
- 예정 변경 파일
- 공개 저장소 여부
- 기존 파일에서 의심되는 개인정보·비밀정보
- 제1호 자산·날짜·콘텐츠의 복사 여부

금지 정보:

- 사용자 개인 정보와 연락처
- 이메일·전화번호·주소·계정 식별자
- 로컬 절대경로
- API 키·토큰·쿠키·인증서·비밀키
- 비공개 일정과 사적인 메모

의심되는 정보가 발견되면 조사·작성·커밋보다 먼저 보고하고 제거한다. 이미 커밋된 비밀은 `.gitignore`만으로 해결하지 않는다.

## 2. 호 메타데이터 확정

조사 전에 다음 값을 작업 메모에 확정한다.

- issue number
- issue start date
- 조사 대상 기간
- 배경 자료 허용 범위
- research cutoff
- 발행 예정 시각과 `Asia/Seoul` timezone
- `archive/YYYY-MM-DD.html`
- `archive/assets/YYYY-MM-DD/`

기본 조사 기간은 직전 주 월요일 00:00부터 일요일 23:59까지다.

- 기간 밖 자료는 배경 또는 후속 확인에만 사용한다.
- 발표일과 사건 발생일을 구분한다.
- 기간 내 발표라도 오래된 계획의 재홍보인지 확인한다.
- 원고 검증 기준 시각 이후 나온 중대한 정정은 발행 전 다시 반영한다.

**산출물:** 공개 저장소에 커밋하지 않는 issue metadata 초안.

## 3. 후보 이슈 조사

Cover, Economy, Politics, Society, Tech의 후보를 각각 최소 3개 수집한다.

각 후보에 기록:

- 사건 또는 결정
- 핵심 1차 자료
- 독자의 판단을 바꿀 이유
- 영향을 받는 주체
- 후속 문서와 검증 가능성
- 다른 섹션·이전 호와의 중복
- 장문·짧은 분석·업데이트 중 적절한 범위

임시 후보표와 미공개 조사 메모는 저장소에 커밋하지 않는다.

**중단 조건:** 공식 원문을 찾지 못한 구체적 사건은 대표 후보에서 제외한다.

## 4. 편집 게이트

### Cover Story

다음 조건을 가장 강하게 충족하는 질문 1개를 선택한다.

- 한 주의 의사결정을 크게 바꾸는가
- 공식 자료와 수치가 충분한가
- 발표 뒤의 실행 경로를 추적할 수 있는가
- 사건 요약보다 구조적 설명 가치가 있는가
- 이전 호 커버와 독립된 새 질문인가

### 분야별 기사

Economy, Politics, Society, Tech는 각 분야의 독립 이슈를 선정한다. 커버와 억지로 묶지 않는다.

선정 뒤 각 기사에 대해 핵심 명제를 한 문장으로 쓴다.

> 이 기사를 읽은 독자가 남겨야 할 핵심 명제:

명제가 추상적이거나 여러 결론을 동시에 포함하면 범위를 줄이거나 후보를 다시 선택한다.

**산출물:** 섹션별 선정 이슈, 핵심 명제와 제외 이유.

## 5. Claim Ledger와 근거표

`SOURCE_POLICY.md`에 따라 기사별 Claim Ledger를 만든다.

다섯 근거 역할:

| 역할 | 필요한 자료 |
|---|---|
| 사건 | 결정·발표·판결·공시 원문 |
| 수치 | 규모·추세·비교 자료 |
| 절차 | 집행·계약·행정·운영 구조 |
| 영향 | 비용·권한·시간·접근성 변화 |
| 반론 | 제약·예외·불확실성·다른 관점 |

- 독립 1차 자료 최소 3개
- 같은 자료가 여러 역할을 담당할 수 있으나 독립 자료 수에서는 한 번만 계산
- 법적 상태·핵심 수치·집행 여부는 1차 자료로 확인
- 영향·반론은 신뢰 가능한 2차 자료로 보완 가능

**중단 조건:** 기사 결론에 필수적인 역할이 비면 장문을 시작하지 않고 범위를 줄인다.

## 6. 원고 작성

모든 원고는 `VOICE_AND_TONE.md`를 따른다.

### 대표 기사

1. 사건과 결정
2. 핵심 명제
3. 작동 구조
4. 실제 영향
5. 반론·한계·불확실성
6. 다음 검증 지점
7. 확인된 사실 / 편집부 해석
8. 공식 출처

### LIFE SCENE

- 가장 분명한 생활 영향 경로를 가진 기사에서 파생한다.
- 가상·합성 사례를 첫 부분과 후단에 고지한다.
- 기사에서 확인된 구조 밖의 극적인 장면을 만들지 않는다.
- 연결 근거가 약하면 절차형 짧은 사례로 전환한다.

### Document Reportage

Economy, Politics, Society, Tech에 각각 1편을 작성한다.

- 경로가 짧으면 `Trace`, 여러 기관·병목을 추적하면 `Full Reportage`
- 대표 기사 문장을 반복하지 않음
- 문서·계약·이동·행정·시간표 중 하나를 선택
- 취재하지 않은 현장 장면과 대화를 만들지 않음
- 이미지 없음

### Data / Watch

- Data는 계획·투입과 집행·성과를 분리한다.
- Watch는 날짜·문서·통계·판단 기준을 적는다.

## 7. Claim Audit와 제목

초고 뒤 Claim Ledger와 문장을 대조한다.

검사:

- 출처 없는 수치와 고유명사
- 출처보다 강한 단정
- 계획을 계약·집행·성과로 바꾼 표현
- 기준일·모집단·통화가 다른 수치의 직접 비교
- 번역 인용의 의미 변화
- 본문 주장과 후단 출처의 불일치
- 상충 자료 누락
- 사실·해석·불확실성 혼동
- 같은 사실·결론·수사 문형 반복

Claim Audit와 검증 메모가 끝난 뒤 제목과 부제를 작성한다.

**산출물:** 감사 완료 원고, 검증 메모, 공식 출처와 최종 제목.

## 8. 모듈 계획

`LAYOUT_SYSTEM.md`와 `TEMPLATE_CONTRACT.md`를 따른다.

기사별로 다음을 기록한다.

- 선택한 기본 모듈
- 필요한 보조 모듈
- 이미지 위치와 비율
- 모듈이 기사 이해를 돕는 이유
- 좁은 화면 전환 방식
- 새 변형 여부

승인 모듈:

- `text-led`
- `image-led-opening`
- `split-opening`
- `evidence-grid`
- `metric-board`
- `process-timeline`
- `document-reportage`

**중단 조건:** 시각적 다양성 외에 변형 이유를 설명할 수 없으면 기본 모듈로 되돌린다.

## 9. 이미지 제작과 매니페스트

`IMAGE_DIRECTION.md`를 따른다.

제작 대상:

- 표지
- LIFE SCENE
- Cover Story
- Economy
- Politics
- Society
- Tech

각 이미지에 매니페스트를 작성한다.

- 대상 섹션
- 핵심 시각 명제
- 파일 경로
- 비율
- alt
- 캡션·생성 이미지 고지
- 피사체 위치
- 글자·숫자·로고·개인정보 검사
- 중복 검사
- 기술 사양

다음 결과는 폐기한다.

- 잡지·웹페이지 전체 목업
- 카툰·벡터·아이콘 조합
- 이미지 내부 글자·숫자·로고
- 기사와 무관한 분위기 장면
- 다른 섹션 이미지 재사용

Document Reportage에는 이미지를 만들거나 넣지 않는다.

## 10. 독립 보존호 조립

새 호는 다음으로 구성한다.

- `archive/YYYY-MM-DD.html`
- `archive/assets/YYYY-MM-DD/`
- 버전 고정 공용 런타임 또는 호별 포함 CSS·JS

`TEMPLATE_CONTRACT.md`의 필수 DOM과 메타데이터를 따른다.

금지:

- 제1호 HTML을 복사한 뒤 일부 텍스트만 교체
- reader 래퍼에서 원본 HTML fetch
- `document.write`
- 기사 본문을 JS에 하드코딩
- 후단 스크립트로 제목·번호·출처 보정
- 여러 fix CSS 누적
- 금지 요소 생성 후 숨김
- 보존호 추가 로딩 화면

보존호는 Cover부터 즉시 시작하고 JS 없이도 전체 본문을 읽을 수 있어야 한다.

## 11. 정적 검증

최소 검사:

- 필수 section과 순서
- 중복 ID
- 깨진 내부 앵커
- 제목 계층
- `data-section`, `data-role`, `data-module`
- 이미지 alt·width·height
- Document Reportage 내부 이미지
- `document.write`
- 보존호 본문 fetch
- JS의 기사 콘텐츠 하드코딩
- 이전 호 날짜·제목·출처·이미지 경로
- 외부 스톡·추적 스크립트
- 이메일·전화번호·로컬 절대경로·인증 문자열·비밀키 패턴
- 보존호·과월호·`latest.json` 메타데이터 일치

**산출물:** 검사 항목별 통과·실패·미확인 기록.

실패 항목이 있으면 다음 단계로 넘어가지 않는다.

## 12. 렌더링·기능·접근성 검수

기준 화면:

- 데스크톱 `1440×1200` 이상
- 태블릿 가로 `1366×1024`
- 태블릿 세로 `1024×1366`
- 모바일 `390×844`

검사:

- 가로 넘침
- 중앙 기준축과 본문 단일 열
- 넓은 화면 Front Spread 40:60
- 좁은 화면 Contents → LIFE SCENE
- 제목·이미지·카드 잘림
- 이미지 핵심 피사체
- topbar와 읽기 진행 바
- 그 외 추적 요소 부재
- 과월호 이동
- 출처 링크
- console error
- broken asset
- 스킵 링크와 키보드 포커스
- 제목 계층과 현재 섹션 상태
- reduced motion
- JS 비활성 상태에서 본문 열람
- 보존호 추가 로딩 화면 부재
- Document Reportage 이미지 부재

가능하면 각 기준 화면의 전체 페이지 캡처를 검수 기록으로 남기되, 로컬 경로와 비공개 정보는 커밋하지 않는다.

직접 확인하지 못한 항목을 통과로 기록하지 않는다.

## 13. 발행 순서

1. 보존호 HTML과 날짜별 자산 추가
2. 정적 검증
3. 렌더링·기능·접근성 검수
4. `archive/index.html`에 새 호 추가
5. 직접 보존호 URL과 과월호 링크 배포 확인
6. `ISSUE_HISTORY.md`에 실제 결과 기록
7. 마지막으로 `latest.json` 갱신
8. 루트 진입에서 새 호 도달 확인

대규모 작업은 여러 커밋으로 나눌 수 있다. 최신호 포인터 변경은 마지막 커밋으로 분리하는 것을 권장한다.

권장 발행 커밋:

```text
Publish WEEKLY SIGNAL YYYY-MM-DD
```

최신호 포인터 커밋:

```text
Point latest issue to YYYY-MM-DD
```

## 14. 배포 후 검증과 롤백

`latest.json` 갱신 후 확인:

- 루트에서 새 독립 보존호로 이동
- 직접 URL 열림
- 과월호 목록에서 새 호 열림
- 날짜·제목·기간 일치
- 이미지와 공용 런타임 로드
- 출처 링크
- 이전 호 링크
- 배포된 commit SHA

실패 시:

1. 원인을 기록한다.
2. 새 보존호 자체가 유효하면 `latest.json`만 이전 값으로 복원할 수 있다.
3. 잘못된 과월호 항목도 함께 수정한다.
4. 비밀정보 노출이면 일반 롤백보다 이력 제거를 우선한다.
5. 복구 후 루트와 직접 URL을 다시 확인한다.

## 15. 발행 후 회고

`ISSUE_HISTORY.md`에는 다음만 기록한다.

- 발행 상태와 커밋
- 최종 주제
- 실제로 사용한 모듈
- 직접 확인한 검수 범위
- 확인된 장점
- 확인된 문제
- 다음 호에서 시험할 사항
- 영구 기준 승격 후보
- 반복하지 않을 주제와 구현

영구 기준을 그대로 반복하지 않는다.

## 16. 실패 처리

- 자료 부족: 약한 주장을 만들지 말고 기사 범위를 줄인다.
- 근거 역할 부족: 장문을 중단하고 짧은 분석이나 업데이트로 전환한다.
- 이미지 생성 실패: 카툰·목업 결과를 사용하지 않고 재생성한다.
- 레이아웃 실패: 새 변형을 폐기하고 승인 기본 모듈로 되돌린다.
- 정적 검사 실패: 발행과 `latest.json` 갱신을 중단한다.
- 렌더링 미확인: 미확인 상태를 보고하고 최신호 포인터를 바꾸지 않는다.
- 링크 오류: 수정 전에는 최신호 포인터를 변경하지 않는다.
- 배포 확인 실패: 이전 `latest.json`으로 롤백한다.
- 비밀 정보 발견: 즉시 커밋을 중단한다. 이미 커밋된 경우 이력 제거 절차를 수행한다.
