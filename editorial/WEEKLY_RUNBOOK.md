# WEEKLY SIGNAL Weekly Runbook

이 문서는 매주 발행 작업의 실행 순서다. 자동화와 수동 작업 모두 이 절차를 따른다.

## 0. 최우선 기준과 보안

작업 시작 전에 다음 문서를 순서대로 읽는다.

1. `editorial/EDITORIAL_STANDARD.md`
2. `editorial/VOICE_AND_TONE.md`
3. `editorial/SOURCE_POLICY.md`
4. `editorial/IMAGE_DIRECTION.md`
5. `editorial/LAYOUT_SYSTEM.md`
6. `templates/TEMPLATE_CONTRACT.md`
7. `editorial/ISSUE_HISTORY.md`
8. 이 문서

저장소의 최신 문서를 대화 기억, 이전 예약 프롬프트와 과거 호의 일회성 구현보다 우선한다.

저장소는 공개 상태다.

- 사용자 개인 정보, 연락처, 계정 정보, 로컬 경로, API 키, 토큰, 쿠키, 비공개 일정과 사적인 메모를 커밋하지 않는다.
- 로컬 작업 메모는 `editorial/private/`, `editorial/local/`, `editorial/scratch/`에만 두며 커밋하지 않는다.
- 커밋 전에 변경 파일에서 이메일, 전화번호, 절대경로, 인증 문자열과 비밀키 패턴을 점검한다.
- 공개 기사에 불필요한 실존 일반인의 개인 식별 정보가 있으면 삭제하거나 일반화한다.

## 1. 조사 기간 확정

기본 조사 기간은 직전 주 월요일 00:00부터 일요일 23:59까지다.

- 기간 밖 자료는 배경 또는 후속 확인에만 사용한다.
- 발표일과 사건 발생일이 다르면 둘을 구분한다.
- 기간 내 발표라도 오래된 계획의 재홍보인지 확인한다.

## 2. 후보 이슈 조사

Cover, Economy, Politics, Society, Tech의 후보를 각각 최소 3개 수집한다.

각 후보에 다음을 기록한다.

- 사건 또는 결정
- 핵심 1차 자료
- 독자의 판단을 바꿀 이유
- 영향을 받는 주체
- 후속 문서와 검증 가능성
- 다른 섹션과의 중복 여부

임시 후보표와 미공개 조사 메모는 저장소에 커밋하지 않는다.

## 3. 편집 게이트

### Cover Story 선정

다음 조건을 가장 많이 충족하는 이슈를 선택한다.

- 한 주의 의사결정을 크게 바꾸는가
- 공식 자료와 수치가 충분한가
- 발표 뒤의 실행 경로를 추적할 수 있는가
- 단순 사건 요약보다 구조적 설명 가치가 있는가
- 이전 호 커버와 중복되지 않는가

### 분야별 대표 기사 선정

경제·정치·사회·테크는 각 분야의 독립 이슈를 선정한다. 커버스토리와 억지로 묶지 않는다.

선정 뒤 각 기사에 대해 다음 한 문장을 작성한다.

> 이 기사를 읽은 독자가 남겨야 할 핵심 명제:

명제가 추상적이거나 여러 결론을 동시에 포함하면 다시 선정하거나 범위를 줄인다.

## 4. 근거표 작성

기사별로 다음 다섯 칸을 채운다.

| 역할 | 필요한 자료 |
|---|---|
| 사건 | 결정·발표·판결·공시 원문 |
| 수치 | 규모·추세·비교를 보여주는 자료 |
| 절차 | 실제 집행·계약·행정 또는 운영 구조 |
| 영향 | 비용·권한·시간·접근성 변화 |
| 반론 | 제약·예외·불확실성 또는 다른 관점 |

핵심 칸이 비어 있으면 장문 기사 작성에 들어가지 않는다.

## 5. 원고 작성

모든 원고는 `VOICE_AND_TONE.md`를 따른다.

### 대표 기사

다음 순서로 작성한다.

1. 무슨 일이 있었는가
2. 핵심 명제
3. 작동 구조
4. 실제 영향
5. 반론과 한계
6. 다음 검증 지점
7. 확인된 사실 / 편집부 해석 메모
8. 공식 출처

### Life Scene

- 가장 분명한 생활 영향 경로를 가진 기사에서 파생한다.
- 가상 인물과 상황의 범위를 명시한다.
- 기사에서 확인된 구조 밖의 극적인 장면을 만들지 않는다.
- 연결 근거가 약하면 절차형 짧은 사례로 전환한다.

### Document Reportage

경제·정치·사회·테크에 각각 1편을 작성한다.

- 대표 기사의 반복을 금지한다.
- 문서·계약·이동·행정·시간표 중 하나를 선택해 순서대로 추적한다.
- 취재하지 않은 현장 장면과 대화를 만들지 않는다.
- 이미지를 넣지 않는다.
- 구성은 내용에 맞춰 타임라인, 문서 경로, 책임표, 단계형 본문 중에서 선택한다.
- 모든 르포를 동일한 카드 그리드로 반복하지 않는다.

### Data / Watch

- Data는 계획·투입과 실제 성과를 구분한다.
- Watch는 확인할 날짜·문서·통계·판단 기준을 적는다.

## 6. 논리 편집

초고가 끝나면 다음을 검사한다.

- 첫 3문단 안에 기사의 핵심 질문과 명제가 드러나는가
- 각 소제목이 앞 논점을 이어가는가
- 같은 사실이 다른 표현으로 반복되지 않는가
- 근거 없이 원인과 결과를 연결하지 않았는가
- 계획을 성과처럼, 총액을 집행액처럼 표현하지 않았는가
- 기사 결론이 제목의 약속과 일치하는가
- 분야별 기사들이 같은 결론을 반복하지 않는가
- 사실·해석·불확실성이 구분되는가

논리 편집이 끝난 뒤 제목을 작성한다.

## 7. 지면 설계

`LAYOUT_SYSTEM.md`와 `templates/TEMPLATE_CONTRACT.md`를 따른다.

초기 단계에서는 하나의 고정 셸을 유지하고 기사 내부만 승인된 모듈로 변형한다.

고정 요소:

- 브랜드 색과 타이포그래피 역할
- 중앙 기준축과 장문 본문 단일 열
- Splash → Cover → Contents+Life Scene → Opening → Cover Story → Economy → Politics → Society → Tech → Data → Watch → Sources & Method 순서
- Contents 40% + LIFE SCENE 60% 프런트 스프레드
- 상단 sticky 내비게이션과 fixed 진행 바
- 검증 메모와 출처의 기사 후단 배치
- 르포 무이미지

기사별로 다음 모듈 중 필요한 최소 조합을 선택한다.

- Text-led
- Image-led Opening
- Split Opening
- Evidence Grid
- Metric Board
- Process / Timeline
- Document Reportage

이미지 위치, 비율, 근거 카드, 데이터 패널과 르포 전개는 내용에 맞게 바꿀 수 있다. 단, 시각적 다양성만을 위해 변형하지 않는다.

새로운 모듈이나 배치를 만들 경우 `ISSUE_HISTORY.md`에 사용 이유와 검수 결과를 기록한다. 최소 두 개 이상의 호에서 효과가 확인되기 전에는 정식 템플릿 규칙으로 승격하지 않는다.

## 8. 이미지 제작

`IMAGE_DIRECTION.md`를 따른다.

제작 대상:

- 표지
- LIFE SCENE
- Cover Story
- Economy
- Politics
- Society
- Tech

각 이미지는 별도로 생성한다. 이미지 생성 결과가 다음에 해당하면 폐기한다.

- 잡지나 웹페이지 전체 목업
- 카툰·벡터·아이콘 조합
- 이미지 내부의 글자·숫자·로고
- 기사와 직접 관계없는 분위기 사진
- 다른 섹션 이미지 재사용

Document Reportage에는 이미지를 넣지 않는다.

이미지 비율과 위치는 `LAYOUT_SYSTEM.md`의 허용 범위 안에서 기사 내용에 맞게 선택한다.

## 9. 웹 조립

현재 저장소의 확정된 브랜드 셸과 기능을 기준으로 조립한다.

기본 순서:

1. Splash
2. Cover
3. Contents 40% + Life Scene 60%
4. Opening
5. Cover Story
6. Economy
7. Politics
8. Society
9. Tech
10. Data
11. Watch
12. Sources & Method

기능 기준:

- 최상단 내비게이션은 sticky
- 주황색 읽기 진행 바는 fixed
- 다른 이미지·카드·메모·정보 레일은 일반 문서 흐름
- 날짜 클릭 시 과월호 이동
- 과월호 최신순 / 1회부터 정렬 유지
- 장문 본문은 단일 열
- 르포는 무이미지

현재 제1호의 누적 패치 구조는 시각 참고 자료로만 사용한다. 제1호의 내용, 날짜, 출처와 이미지 경로를 복사하지 않는다.

새 호는 가능한 한 `archive/YYYY-MM-DD.html` 하나로 완결되는 독립 보존호로 만든다. 임시 후삽입 스크립트와 버전별 보정 파일 의존을 늘리지 않는다.

정식 `templates/issue-template.html`이 만들어지기 전에는 `TEMPLATE_CONTRACT.md`를 구조 계약으로 사용한다. 정식 템플릿이 생긴 뒤에는 그 파일을 복사해 콘텐츠와 자산만 교체한다.

## 10. 검수

### 내용 검수

- [ ] 커버와 분야별 대표 이슈가 독립적으로 가치가 있는가
- [ ] 기사별 핵심 명제가 한 문장으로 설명되는가
- [ ] 역할이 다른 1차 근거가 최소 3개인가
- [ ] 반론과 한계가 있는가
- [ ] 제목과 본문이 일치하는가
- [ ] Life Scene의 근거 연결이 분명한가
- [ ] 르포가 대표 기사를 반복하지 않는가
- [ ] 계획·계약·집행·성과가 구분되는가
- [ ] 문체가 `VOICE_AND_TONE.md`와 일치하는가
- [ ] 개인 정보나 비밀 정보가 없는가

### 레이아웃 검수

- [ ] 고정 셸과 전체 순서가 유지되는가
- [ ] 선택한 모듈이 기사 논리를 명확하게 하는가
- [ ] 모든 기사가 같은 템플릿을 기계적으로 반복하지 않는가
- [ ] 섹션마다 전혀 다른 사이트처럼 보이지 않는가
- [ ] 이미지 위치와 비율이 기사 내용에 맞는가
- [ ] 르포 구성이 추적 대상의 경로와 맞는가
- [ ] 제1호의 콘텐츠나 자산 경로가 남아 있지 않은가

### 화면 검수

다음 화면을 기준으로 확인한다.

- 데스크톱 1440px
- 태블릿 세로 1024×1366
- 태블릿 가로 1366×1024

검사항목:

- [ ] 가로 넘침 없음
- [ ] 본문 단일 열
- [ ] 프런트 스프레드 40:60
- [ ] 좁은 화면에서 Contents → Life Scene 1열
- [ ] 제목·이미지·카드 잘림 없음
- [ ] 중앙 기준축 일치
- [ ] 내비게이션과 진행 바 동작
- [ ] 그 외 추적 요소 없음
- [ ] 과월호 링크와 정렬 동작
- [ ] 르포 이미지 없음
- [ ] 출처 링크 열림
- [ ] 스플래시 최소 2초, 추가 로딩 화면 없음

직접 확인하지 못한 검수 항목을 통과했다고 기록하지 않는다.

## 11. 커밋과 발행 순서

1. 새 보존호와 자산 추가
2. 레이아웃·콘텐츠 검수
3. `archive/index.html`에 새 호 추가
4. `ISSUE_HISTORY.md`에 발행 회고와 레이아웃 실험 결과 추가
5. 마지막으로 `latest.json` 변경

어느 단계라도 실패하면 `latest.json`을 바꾸지 않는다.

권장 커밋 메시지:

```text
Publish WEEKLY SIGNAL YYYY-MM-DD
```

대규모 작업에서 여러 커밋이 필요하면 마지막 커밋은 최신호 포인터 갱신임을 명확히 표시한다.

## 12. 발행 후 회고

`ISSUE_HISTORY.md`에 다음을 기록한다.

- 최종 주제
- 유지할 점
- 개선할 점
- 다음 호에 적용할 구체적인 규칙
- 반복하지 않을 주제와 표현
- 사용한 기사 모듈과 새 레이아웃 변형
- 데스크톱·태블릿 검수 결과
- 변형을 재사용할 가치가 있는지 여부

사용자의 피드백이 들어오면 해당 호 기록에 먼저 반영한다. 여러 호에서 반복되는 원칙만 영구 기준 문서로 옮긴다.

## 13. 실패 처리

- 자료 부족: 약한 주장을 만들지 말고 기사 범위를 줄인다.
- 이미지 생성 실패: 카툰·목업 결과를 사용하지 않고 재생성한다.
- 레이아웃 실패: 새 변형을 폐기하고 승인된 기본 모듈로 되돌린다.
- 렌더링 미확인: 미확인 사실을 최종 보고에 명시한다.
- 링크 오류: 수정 전에는 최신호 포인터를 변경하지 않는다.
- 비밀 정보 발견: 즉시 커밋을 중단하고 제거한다. 이미 커밋된 경우 `.gitignore`만으로 해결되지 않으므로 기록 제거 절차를 별도로 수행한다.
