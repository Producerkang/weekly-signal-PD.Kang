# WEEKLY SIGNAL 주간 발행 절차

이 문서는 한 호를 조사·작성·편집·검수·승인·배포하는 실행 순서를 규정한다. 공개 경로와 브랜치 절차는 `PUBLISHING_PIPELINE.md`, 콘텐츠 통과 여부는 `ISSUE_QUALITY_GATE.md`, 자동 구조 검사는 `tools/validate_repository.py`가 결정한다.

## 1. 시작 조건

새 회차를 시작하기 전에 다음을 먼저 수행한다.

1. 최신 `main`을 기준으로 `issue/YYYY-MM-DD` 브랜치를 만든다.
2. `main`에서 직접 회차를 제작하지 않는다.
3. 조사·집필·이미지 후보와 중간 렌더링은 작업 브랜치에서만 관리한다.
4. 모든 콘텐츠와 화면이 완성되기 전에는 `archive/YYYY-MM-DD/`를 만들지 않는다.

새 회차를 시작할 때 다음 문서를 순서대로 읽는다.

1. `editorial/PUBLISHING_PIPELINE.md`
2. `editorial/EDITORIAL_STANDARD.md`
3. `editorial/ISSUE_QUALITY_GATE.md`
4. `editorial/SECTION_AND_DEEP_DIVE_STANDARD.md`
5. `editorial/HEADLINE_AND_EDITORS_PICK_STANDARD.md`
6. `editorial/VOICE_AND_TONE.md`
7. `editorial/SOURCE_POLICY.md`
8. `editorial/IMAGE_DIRECTION.md`
9. `editorial/LAYOUT_SYSTEM.md`
10. `templates/TEMPLATE_CONTRACT.md`
11. `templates/NAVIGATION_CONTRACT.md`

HTML 제작 단계에서 `templates/ISSUE_TEMPLATE.html`을 시작 셸로 사용한다. 템플릿은 완성 디자인이 아니라 구조적 시작점이다.

## 2. 기본 구성 잠금

별도 사용자 지시가 없으면 다음 구성을 유지한다.

- Cover Story 1편
- Economy 일반 기사 1편
- Politics 일반 기사 1편
- Society 일반 기사 1편
- Tech 일반 기사 1편
- DEEP DIVE 1~2편
- LIFE SCENE 1편
- EDITOR'S PICK 1편
- Sources

Cover Story가 특정 분야를 다뤄도 해당 분야 일반 기사를 생략하지 않는다. DEEP DIVE, LIFE SCENE, DATA와 WATCH는 일반 기사 수에 포함하지 않는다. 기사 후보가 부족하면 리서치를 계속하며 분야를 삭제해 축소 발행하지 않는다.

## 3. 리서치

1. 대상 주간의 주요 이슈를 분야별로 수집한다.
2. Cover Story와 각 기본 분야에서 후보를 최소 2개 이상 검토한다.
3. 핵심 사실·수치·법적 상태·계약·시행 여부를 공식 1차 자료로 확인한다.
4. 발표·검토·계획·MOU·계약·시행·집행·성과·전망·편집적 해석을 구분한다.
5. 보도자료 외에 법령·결정문·예산·통계·담당기관 자료와 신뢰할 수 있는 반론을 조사한다.
6. 주요 기사마다 사건·수치·절차·영향·반론을 담당할 근거를 확보한다.
7. Cover Story와 분야별 기사 간 주제가 과도하게 겹치지 않는지 확인한다.

다음이 충족되기 전에는 집필하지 않는다.

- Cover Story와 4개 분야 기사 후보가 모두 선정됨
- 각 기사에 사건·수치·절차·영향·반론 근거가 있음
- 대표 기사와 주요 일반 기사에 독립 1차 자료가 원칙적으로 3개 이상 있음

## 4. 일반 기사 전체 작성

1. Cover Story와 Economy·Politics·Society·Tech를 모두 작성한다.
2. 독자가 핵심 용어를 처음 접한다고 가정한다.
3. 핵심 사실, 오해 교정, 정의, 배경, 작동 구조, 적용 범위, 실제 영향, 상태 구분, 반론과 후속 판단 기준을 본문 안에서 완결한다.
4. 공식 문서의 배열이 아니라 독자의 질문 순서로 재구성한다.
5. 기사마다 독립적으로 사실 검증하고 문장을 개정한다.
6. 모든 기사가 동일한 소제목 수와 문단 리듬을 갖지 않게 한다.
7. 본문이 카드·이미지·디자인 없이도 독립적인 읽을 가치가 있을 때만 다음 단계로 간다.

이 단계에서는 DEEP DIVE, LIFE SCENE, EDITOR'S PICK, 이미지와 HTML을 만들지 않는다.

## 5. DEEP DIVE 선정·작성

1. 완성된 일반 기사 전체를 읽고 심화가 필요한 기사를 고른다.
2. `심화 차이 메모`에 일반 기사가 이미 답한 질문을 적는다.
3. DEEP DIVE가 새로 답할 한 가지 심화 질문을 확정한다.
4. 새 핵심 주장 최소 3개와 일반 기사에 없던 독립 출처 최소 2개를 확보한다.
5. 쟁점 대립·정책 필요성·구조 해부·결과 시나리오·역사 비교 중 적합한 형식을 선택한다.
6. 같은 정의·원인·경로·결론을 반복하지 않는다.

DEEP DIVE를 제거해도 일반 기사가 완결돼야 하며, 반대로 DEEP DIVE를 제거했을 때 독자가 잃는 새 지식이 분명해야 한다.

## 6. LIFE SCENE 선정·작성

1. 일반 기사와 DEEP DIVE가 완성된 뒤 주제를 고른다.
2. 개인 선택이나 주의로 해결되는 문제가 아니라 외부 제도·기관·서비스의 생활 문제인지 확인한다.
3. 평범한 일상, 현실적 가상 인물, 제한된 정보, 기대와 실제의 차이를 중심으로 쓴다.
4. 대기·이동·비용·정보 부족·일정 변경·돌봄·책임 공백 중 최소 세 가지가 자연스럽게 누적되게 한다.
5. 제목과 부제는 생활 장면을 중심으로 쓴다.
6. 마지막 `SCENARIO NOTE`에서만 정책과 기사 연결을 설명한다.
7. 개인 투자·소비·자기관리 조언으로 끝내지 않는다.

## 7. EDITOR'S PICK 작성

전체 원고가 완성된 뒤 마지막 원고로 쓴다.

1. 실제로 판단이 바뀐 한 지점 또는 오래 남은 한 사실을 중심축으로 고른다.
2. 모든 기사를 언급하려 하지 않는다.
3. 기사명보다 편집 과정의 판단과 감정을 쓴다.
4. 한 문단에 기사 하나씩 배치하지 않는다.
5. 기사 요약을 억지 공통 교훈으로 묶지 않는다.

## 8. 지면 설계

1. DATA와 WATCH는 새로운 정보가 있을 때만 만든다.
2. 대표 기사의 표지 주제를 확정한다.
3. 기사마다 내용에 맞는 지면 조합을 선택한다.
4. 한 호에 최소 세 가지 이상의 기사 레이아웃 리듬을 만든다.
5. 템플릿의 동일 구조를 모든 기사에 복제하지 않는다.
6. 시각 모듈은 본문을 반복하지 않고 새 정보를 제공해야 한다.

## 9. 이미지 제작

1. 모든 주요 이미지를 실제 이미지 생성 모델로 새로 만든다.
2. 표지·Cover Story·각 분야 기사·DEEP DIVE·LIFE SCENE에 서로 다른 역할과 구도를 부여한다.
3. 표지는 장변 1800px 이상, 나머지 주요 이미지는 장변 1600px 이상을 사용한다.
4. Python·Canvas·CSS·SVG 도형을 래스터로 만든 대체 이미지를 사용하지 않는다.
5. 외부 이미지 URL을 HTML에 직접 연결하지 않는다.
6. 생성 결과를 WebP·PNG·JPEG 파일로 저장해 회차의 `assets/`에 둔다.
7. 각 파일을 실제로 열어 얼굴·손·장비·문자 오류와 디테일을 확인한다.
8. 장변 1600px 이상인데 80KB 미만인 파일은 사용하지 않고 다시 생성한다.
9. 데스크톱과 모바일 크롭을 확인한다.

이미지에 실패하면 임시 그래픽이나 외부 URL로 대체하지 않는다.

## 10. 발행 후보 HTML 제작

원고·이미지·지면 설계와 육안 검수가 끝난 뒤에만 작업 브랜치에서 `archive/YYYY-MM-DD/`를 만든다.

허용 구조:

```text
archive/YYYY-MM-DD/
├─ index.html
└─ assets/
```

1. 완성된 본문·CSS·최소 JavaScript를 `index.html` 하나에 넣는다.
2. 별도 CSS·JS·분할 HTML·이미지 매니페스트를 두지 않는다.
3. `fetch()` 또는 `XMLHttpRequest`로 기사 본문을 조립하지 않는다.
4. 이미지는 `./assets/...` 상대경로만 사용한다.
5. DEEP DIVE는 관련 일반 기사 바로 뒤에 둔다.
6. 목차·내비게이션·DOM 순서를 일치시킨다.
7. 미사용 클래스, 숨겨진 모듈과 임시 주석을 삭제한다.

## 11. 실제 화면 검수

다음 화면을 실제 렌더링하거나 캡처해 확인한다.

- 1440px 이상
- 1366px
- 1024px
- 390px

확인 항목:

- Cover 제목 안전영역과 이미지 선명도
- 기본 구성과 Contents 일치
- 기사별 시각적 차이
- DEEP DIVE의 새 지식과 배치
- LIFE SCENE 서사 흐름
- 이미지 디테일과 크롭
- 표·카드·제목 오버플로
- 링크와 상대경로

HTML 코드만 읽고 화면 검수를 통과했다고 기록하지 않는다.

## 12. 자동 검증

발행 메타데이터는 마지막에 갱신한다.

1. `issues.json` 맨 앞에 새 회차 추가
2. `latest.json`을 같은 객체로 변경
3. `archive/index.html`에 필요한 반영 확인
4. `ISSUE_HISTORY.md`에 발행 후보 기록

그 후 다음 명령을 실행한다.

```bash
python -m pip install -r requirements-ci.txt
python tools/validate_repository.py
python tools/build_public_site.py
```

검증기는 발행 목록과 `archive/`의 날짜 폴더를 정확히 대조한다. 발행 목록에 없는 회차 폴더, 외부 이미지 URL, 별도 CSS·JS, 분할 HTML, 필수 기사와 이미지 누락이 하나라도 있으면 실패한다.

## 13. PR과 사용자 승인

1. 회차 전용 브랜치에서 PR을 연다.
2. `Publication quality gate`가 통과했는지 확인한다.
3. 제1호와 새 회차를 나란히 비교해 밀도·리듬·이미지 품질을 점검한다.
4. 완성 화면을 사용자에게 제시한다.
5. 사용자의 명시적인 발행 승인을 받는다.

승인 전에는 PR을 병합하지 않는다. 자동 검증 통과는 사용자 승인이나 편집 품질 검토를 대신하지 않는다.

## 14. 병합과 배포

1. 승인된 PR만 `main`에 병합한다.
2. GitHub Actions에서 `Deploy approved publication`을 수동 실행한다.
3. 확인 입력에 `PUBLISH`를 정확히 입력한다.
4. 배포 후 공개 URL에서 최신호·과월호·모바일 화면을 다시 확인한다.

Pages는 `GitHub Actions` 배포 소스를 사용한다. `main / (root)` 직접 배포는 사용하지 않는다.

## 15. 실패 처리

검증 또는 사용자 검토에 실패하면:

- PR을 병합하지 않는다.
- `main/archive/`에 실패본을 남기지 않는다.
- `issues.json`과 `latest.json`에 추가하지 않는다.
- 작업 브랜치에서 원고·이미지·HTML을 다시 만든다.
- 실패본은 작업 브랜치와 Git 이력에만 남긴다.

동일 회차를 다시 만들 때도 완성 전에는 공개 경로를 사용하지 않는다.
