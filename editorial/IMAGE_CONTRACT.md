# WEEKLY SIGNAL 이미지 계약

이 문서는 WEEKLY SIGNAL의 이미지 계획·생성·검수·저장에 대한 **유일한 현행 계약**이다.

이미지 관련 실행과 품질 판단은 이 문서만 기준으로 한다. 회차별 슬롯·파일명·비율·장면은 해당 회차의 `IMAGE_PLAN.md`와 `image_prompts/*.txt`가 소유한다.

핵심 원칙은 하나다.

> **운영 문맥과 이미지 생성 문맥을 분리한다.**

이미지를 잘 만들기 위해 저장소 상태를 더 많이 설명하지 않는다. 실제 생성 직전에는 현재 슬롯의 순수 장면 프롬프트만 남긴다.

---

## 1. 전체 구조

이미지 작업은 두 예약 작업으로 분리한다.

```text
07:00  LAYOUT / IMAGE PREPARATION
        ↓
08:00  IMAGE GENERATION
```

### 07:00 — 지면 설계와 이미지 입력 준비

07:00은 **텍스트·파일 작업 전용**이다. 이미지 생성은 하지 않는다.

필수 산출물:

```text
work/YYYY-MM-DD/
├─ LAYOUT_PLAN.md
├─ IMAGE_PLAN.md
└─ image_prompts/
   ├─ 01_*.txt
   ├─ 02_*.txt
   └─ ...
```

완료 조건:

- `LAYOUT_PLAN.md`: `COMPLETE`
- `IMAGE_PLAN.md`: `READY`
- 모든 생성 대상 슬롯에 대응하는 `image_prompts/*.txt` 존재
- `WORK_STATE.md`: `LAYOUT: COMPLETE`, `IMAGES: PENDING`
- 다음 작업: `08:00 이미지 슬롯별 순차 제작`

### 08:00 — 이미지 생성 전용

08:00은 지면을 설계하지 않는다. 기사 장면을 새로 기획하지 않는다.

07:00에서 이미 확정된 `IMAGE_PLAN.md`와 슬롯별 프롬프트 파일을 실행한다.

```text
1 SLOT = 1 PROMPT FILE = 1 SCENE = 1 IMAGE
```

한 턴 안에서 여러 슬롯을 순서대로 처리하지만, 이미지 생성 호출 하나는 항상 현재 슬롯 한 장만 다룬다.

---

## 2. IMAGE_PLAN 계약

`IMAGE_PLAN.md`는 **이미지 큐와 상태만 관리하는 제어 문서**다.

이미지 장면을 장문으로 설명하지 않는다. 실제 생성 문장은 별도 `.txt` 파일에 둔다.

권장 구조:

```md
# ISSUE IMAGE PLAN

status: READY
layout_dependency: COMPLETE

| order | slot | prompt_file | output_file | state | attempts | ratio | target |
|---:|---|---|---|---|---:|---|---:|
| 1 | Cover | image_prompts/01_cover.txt | cover.webp | READY | 0/3 | flexible | 2200px+ |
| 2 | Life Scene | image_prompts/02_life.txt | life-scene.webp | READY | 0/3 | 4:3 | 2000px+ |
```

허용 상태:

- `READY`
- `GENERATED`
- `ACCEPTED`
- `RETRY`
- `BLOCKED`
- `SAVED`
- `INTEGRATED`
- `PLAN_INVALID`

`IMAGE_PLAN.md`에 기사 원고 전체, 작업 보고서, 장면 프롬프트 전문을 복사하지 않는다.

---

## 3. 슬롯 프롬프트 파일 계약

각 생성 대상 슬롯은 독립된 UTF-8 텍스트 파일 하나를 가진다.

예:

```text
work/YYYY-MM-DD/image_prompts/01_cover.txt
work/YYYY-MM-DD/image_prompts/02_life-scene.txt
work/YYYY-MM-DD/image_prompts/03_cover-story.txt
```

### 3.1 파일 안에 들어갈 것

프롬프트 파일은 **이미지로 보일 내용만** 기술한다.

- 실제 세계의 한 장면 또는 공간
- 중심 피사체와 행동 또는 사물
- 카메라 거리·높이·구도
- 자연스럽거나 약간 시네마틱한 빛
- 현실적인 재질·원근·공간감
- 필요한 여백 또는 안전영역
- 필요한 경우 비율
- 필요한 경우 짧은 하드 제약

장면은 가능한 한 긍정형 문장으로 직접 묘사한다.

좋은 방향:

```text
A photorealistic editorial photograph of an empty formal conference room...
```

### 3.2 파일 안에 넣지 않을 것

프롬프트 파일에는 **운영 정보나 문서 구조를 넣지 않는다.**

다음 종류의 정보는 이미지 프롬프트 파일 밖에 둔다.

- 프로젝트·저장소·브랜치 정보
- 회차·예약 작업·진행 상태
- 파일 경로·커밋·체크리스트
- 문서·UI·리포트 구성 지시
- 기사 제목을 그대로 그래픽으로 표현하라는 지시
- 이미지 제작 과정 설명

프롬프트 파일은 제목·표·체크박스가 없는 **순수 장면 문장**이어야 한다.

### 3.3 길이

보통 60~180단어 정도면 충분하다.

프롬프트가 길어질수록 작업 설명을 추가하지 말고 장면의 공간·피사체·광원·카메라 정보를 더 명확히 한다.

---

## 4. 08:00 실행 알고리즘

08:00 이미지 턴의 기본 실행은 다음과 같다.

```text
IMAGE_CONTRACT 확인
→ IMAGE_PLAN 확인
→ 첫 READY / RETRY 슬롯 선택
→ 해당 prompt_file 읽기
→ 즉시 이미지 1장 생성
→ 실제 픽셀 육안 검수
→ 상태 기록
→ 다음 슬롯 선택
→ 다음 prompt_file 읽기
→ 즉시 이미지 1장 생성
→ 반복
```

### 4.1 읽기 범위

08:00 턴은 기본적으로 다음만 읽는다.

1. `editorial/IMAGE_CONTRACT.md`
2. 해당 회차 `IMAGE_PLAN.md`
3. 현재 슬롯의 `image_prompts/*.txt`

`LAYOUT_PLAN.md`, 기사 원고, `WORK_STATE.md`는 **이미지 장면을 다시 해석하기 위해 읽지 않는다.**

선행 상태 확인이 정말 필요하면 작업 시작 시 한 번만 최소한으로 확인하고, 이미지 호출 직전에는 다시 읽지 않는다.

### 4.2 마지막 읽기 규칙

이미지 생성 도구를 호출하기 직전에 읽는 마지막 파일은 반드시 **현재 슬롯의 프롬프트 `.txt`**다.

그 파일을 읽은 뒤 이미지가 반환될 때까지:

- 다른 저장소 파일을 읽지 않는다.
- 상태 보고를 작성하지 않는다.
- 장면을 업무 설명으로 다시 풀어쓰지 않는다.

### 4.3 생성 지시 규칙

이미지 생성 지시는 현재 슬롯 프롬프트 파일의 장면 내용만 사용한다.

프롬프트 앞뒤에 작업 보고, 파일명 설명, 잡지 제작 설명을 덧붙이지 않는다.

한 번의 호출에서 여러 슬롯이나 여러 후보를 요구하지 않는다.

### 4.4 계획이 불완전할 때

프롬프트 파일이 없거나 장면이 불명확하면 이미지를 임의 생성하지 않는다.

해당 슬롯을 `PLAN_INVALID`로 기록하고 다음 슬롯로 이동한다.

---

## 5. 생성 결과 계약

정상 결과는 **프레임 전체가 하나의 독립된 사진적 에디토리얼 장면**이다.

이미지 자체가 기사 지면에 바로 삽입될 수 있어야 한다.

다음 두 조건만 먼저 확인한다.

1. 한 장면인가?
2. 사진적 에디토리얼 이미지인가?

둘 중 하나라도 아니면 `NON_SCENE_OUTPUT` 실패다.

텍스트·UI·문서·리포트가 화면의 주된 구조인 결과는 기사 이미지로 채택하지 않는다.

실패 이미지는 발행 자산으로 저장하지 않고 유효한 품질 후보로 계산하지 않는다.

---

## 6. 실사용 품질선

목표는 실제 잡지 지면에서 충분히 자연스럽고 선명한 이미지다.

PASS 가능:

- 현실적인 카메라 시점
- 중심 장면이 한눈에 읽힘
- 재질·빛·원근·공간감이 자연스러움
- 눈에 띄는 생성 오류가 없음
- 기사 주제와 자연스럽게 연결됨
- 실제 지면에서 크롭 가능한 구성
- 광고용 스톡 이미지처럼 과장되지 않음

기사의 모든 메커니즘을 한 장 안에 설명할 필요는 없다.

현재 기사와 자연스럽게 연결되고 오해를 만들지 않으면 충분하다.

합격권 이미지가 나오면 더 화려한 후보를 찾기 위한 재생성을 하지 않는다.

---

## 7. 섹션별 하드 규칙

### Cover

- 대표 기사와 자연스럽게 연결되는 강한 장면
- 제목을 올릴 여백 고려
- Cover Story 본문 이미지와 다른 원본·거리·구도
- 완성된 잡지 표지 자체가 아니라 **배경으로 사용할 독립 이미지** 생성

### Politics / Politics Deep Dive

**완전 무인**이다.

프레임 안 어디에도 사람, 얼굴, 실루엣, 손·신체 일부가 없어야 한다. 반사면·화면·사진 속 인물도 허용하지 않는다.

정치 프롬프트에는 장황한 금지 목록 대신 다음과 같이 장면 자체를 무인 공간으로 설계한다.

```text
An empty formal government conference room with no people anywhere in the frame...
```

### LIFE SCENE

- 한국의 자연스러운 생활 공간과 평범한 행동
- 광고형 포즈보다 실제 생활 순간
- 생성 전에 가로 `4:3` 또는 세로 `4:5` 중 하나만 확정

### 일반 기사 / DEEP DIVE

생산·유통·업무·생활 서비스·연구 인프라 등 기사에 연결되는 실제 공간과 사물을 우선한다.

정확한 수치·절차·정책 관계는 HTML 조판이 담당한다.

---

## 8. 해상도

새 생성 목표:

- Cover: 장변 `2200px` 이상
- 나머지 주요 이미지: 장변 `2000px` 이상

목표보다 약간 낮더라도 실제 지면에서 충분히 선명하고 크롭 여유가 있으면 편집 판단으로 채택할 수 있다.

단순 확대만으로 규격을 맞추지 않는다.

---

## 9. 재시도

한 슬롯의 유효 이미지 시도는 기본 최대 3회다.

1. 첫 생성
2. 실패 원인을 반영한 재생성
3. 필요하면 장면·거리·구도를 바꾼 마지막 시도

`NON_SCENE_OUTPUT`처럼 기사 이미지 자체가 아닌 결과는 유효 품질 시도로 계산하지 않는다.

3회의 유효 시도 뒤에도 통과하지 못하면 `BLOCKED`로 기록하고 다음 슬롯로 이동한다.

한 슬롯 실패 때문에 이미 통과한 다른 슬롯을 다시 생성하지 않는다.

---

## 10. 저장과 완료

생성 후보와 실패본은 작업 환경에서만 다룬다.

`archive/YYYY-MM-DD/assets/`에는 `ACCEPTED`된 최종 사용 이미지와 실제 발행 파일만 둔다.

이미지 단계 COMPLETE 조건:

- 모든 REQUIRED 슬롯이 `ACCEPTED` 또는 `SAVED`
- 동일 이미지 재사용 없음
- Politics 계열 슬롯 완전 무인
- LIFE SCENE 비율 적합
- 실제 지면 사용에 충분한 해상도와 디테일

최종 발행은 HTML에 반영한 뒤 실제 화면 검수까지 통과해야 한다.

---

## 11. 회차 독립성

이 계약에는 특정 회차의 슬롯 수, 기사 제목, 파일명, 장면을 고정하지 않는다.

회차별 결정은 다음이 소유한다.

- `LAYOUT_PLAN.md`: 지면과 슬롯 역할
- `IMAGE_PLAN.md`: 이미지 큐와 상태
- `image_prompts/*.txt`: 실제 생성 장면

과거 이미지와 승인된 시연 결과는 품질 감각 참고용일 뿐 복제 템플릿이 아니다.
