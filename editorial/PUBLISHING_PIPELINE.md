# WEEKLY SIGNAL 발행 절차

이 문서는 회차 제작 파일이 공개 사이트에 노출되는 과정을 규정한다. **GitHub Actions, 작업 브랜치와 PR을 기본 제작 절차로 사용하지 않는다.** 발행 품질은 제작자가 원고·이미지·지면과 실제 화면을 직접 검수해 결정한다.

## 1. 작업 위치

- 조사 메모, 원고 초안, 이미지 후보, 중간 HTML, 렌더링 캡처와 검수 파일은 GitHub 저장소 밖의 작업 환경에서 처리한다.
- `main`에는 승인 대기본이나 중간 산출물을 두지 않는다.
- `archive/YYYY-MM-DD/`에는 완성된 `index.html`과 최종 래스터 이미지 자산만 둔다.
- 완성 전 상태를 `main`에 먼저 올리고 순차 수정하는 방식은 사용하지 않는다.

## 2. 조사·집필 단계

- 직전 회차와 실패 기록을 확인하고 이번 회차의 품질 향상 목표를 세운다.
- 일반 기사 전체를 먼저 작성하고 검증한다.
- 이후 DEEP DIVE, LIFE SCENE, EDITOR'S PICK 순서로 작성한다.
- 이미지와 HTML은 본문이 완성된 뒤 제작한다.
- 기사 수를 맞추기 위해 약한 원고를 넣거나 분야를 임의로 삭제하지 않는다.

품질 향상 목표에는 최소한 다음 세 축이 포함되어야 한다.

1. 원고 깊이와 정보 밀도
2. 이미지 디테일과 기사별 시각 차이
3. 지면 리듬과 모바일 읽기 경험

## 3. 발행 후보 구성

모든 원고·이미지·지면이 완성된 뒤에만 다음 구조를 만든다.

```text
archive/YYYY-MM-DD/
├─ index.html
└─ assets/
   ├─ cover.webp
   └─ ...
```

회차 루트에는 `index.html`과 `assets/`만 둔다.

- CSS와 최소 JavaScript는 `index.html`에 내장한다.
- 기사 본문을 별도 HTML 파일이나 `fetch()`로 조립하지 않는다.
- 모든 주요 이미지는 회차의 `assets/`에 저장한다.
- 외부 이미지 URL을 직접 사용하지 않는다.

## 4. 제작자 직접 검수

사용자가 매 회차를 직접 검수하지 않아도 되도록 제작자가 아래 항목의 최종 책임을 맡는다.

### 원고

- Cover Story와 분야별 일반 기사 전체가 있는가
- 각 기사가 보도자료 정리에 머물지 않는가
- DEEP DIVE가 일반 기사를 반복하지 않는가
- LIFE SCENE이 개인 조언으로 끝나지 않는가
- EDITOR'S PICK이 기사별 요약이 아닌가
- 출처와 사실 상태가 정확한가
- 직전 회차보다 질문과 정보 밀도가 개선됐는가

### 이미지

- 모든 이미지가 실제 래스터 생성 이미지인가
- 벡터풍·플랫·아이콘형 결과가 아닌가
- 얼굴·손·장비·문자 오류가 없는가
- 기사마다 다른 장면과 구도를 사용하는가
- 데스크톱과 모바일 크롭이 적절한가
- 직전 회차보다 디테일과 편집 적합성이 개선됐는가

### 지면

- 완성된 잡지로 보이는가
- 기사마다 시각적 리듬이 실제로 다른가
- 장식 모듈이 본문을 반복하지 않는가
- 1440px, 1366px, 1024px, 390px 화면에서 문제가 없는가
- 제1호와 직전 회차보다 현저히 얇거나 단순해지지 않았는가
- 긴 블로그 문서가 아니라 매거진으로 읽히는가

## 5. 보조 구조 검사

필요하면 다음 명령을 직접 실행한다.

```bash
python -m pip install -r requirements-tools.txt
python tools/validate_repository.py
```

검사기는 다음과 같은 기술적 실수를 찾는다.

- `issues.json`과 `archive/` 불일치
- `latest.json` 불일치
- 별도 CSS·JS·분할 HTML
- 런타임 기사 조립
- 외부 이미지 URL과 로컬 자산 누락
- 필수 섹션·이미지·앵커 누락
- 이미지 해상도·파일 크기·중복 문제

검사 통과는 발행 품질 통과와 동일하지 않다. 검사기는 기사 깊이, 이미지 미감과 지면 완성도를 판단하지 못한다.

## 6. `main` 직접 반영

제작자 직접 검수를 모두 통과한 뒤 한 번에 다음을 `main`에 반영한다.

1. 완성된 `archive/YYYY-MM-DD/`
2. `issues.json`
3. `latest.json`
4. `archive/index.html`
5. `ISSUE_HISTORY.md`

사용자에게 매번 사전 승인을 요구하지 않는다. 사용자는 발행 후 결과를 보고 방향과 품질 기준을 계속 높일 수 있으며, 그 피드백은 다음 수정과 회차 제작 기준에 즉시 반영한다.

GitHub Pages는 `main` 브랜치 루트의 정적 파일을 그대로 사용한다. 별도 Actions 빌드·배포 과정은 없다.

## 7. 실패 처리

품질 검수에 실패하면:

- `main`에 반영하지 않는다.
- 공개 `archive/`에 실패본을 남기지 않는다.
- 작업 환경에서 원고·이미지·HTML을 다시 만든다.
- 기술적 조건만 맞추는 우회 수정은 하지 않는다.

외부 이미지가 준비되지 않았거나 실제 렌더링을 확인하지 못한 상태는 발행 불가다.
