# WEEKLY SIGNAL 발행 절차

이 문서는 회차 제작 파일이 공개 사이트에 노출되는 과정을 규정한다. **GitHub Actions는 사용하지 않는다.** 자동화는 구조 검사의 보조 수단일 뿐이며, 발행 품질은 원고·이미지·지면을 직접 검수해 결정한다.

## 1. 작업 위치

### `main`

- 승인된 발행본과 현행 제작 기준만 둔다.
- `archive/YYYY-MM-DD/`에는 `issues.json`에 등록된 완성 회차만 존재해야 한다.
- 미완성 HTML, 외부 이미지 URL, 임시 CSS·JS와 분할 기사 파일을 두지 않는다.

### `issue/YYYY-MM-DD`

- 새 회차 제작에 사용하는 작업 브랜치다.
- 항상 최신 `main`에서 시작한다.
- 조사 메모, 이미지 후보와 중간 HTML은 이 브랜치에서만 관리한다.
- 작업 브랜치는 공개 발행본으로 간주하지 않는다.

작업 브랜치를 사용하는 목적은 자동화가 아니라 미완성 회차가 공개 `main`에 섞이지 않게 하는 것이다.

## 2. 조사·집필 단계

- 공개 경로인 `archive/`에 회차 폴더를 먼저 만들지 않는다.
- 일반 기사 전체를 먼저 작성하고 검증한다.
- 이후 DEEP DIVE, LIFE SCENE, EDITOR'S PICK 순서로 작성한다.
- 이미지와 HTML은 본문이 완성된 뒤 제작한다.
- 기사 수를 맞추기 위해 약한 원고를 넣거나 분야를 임의로 삭제하지 않는다.

## 3. 발행 후보 구성

모든 원고·이미지·지면이 완성된 뒤에만 다음 구조를 만든다.

```text
archive/YYYY-MM-DD/
├─ index.html
└─ assets/
   ├─ cover.webp
   └─ ...
```

회차 루트에는 `index.html`과 `assets/`만 둔다.

- CSS와 최소 JavaScript는 `index.html`에 내장한다.
- 기사 본문을 별도 HTML 파일이나 `fetch()`로 조립하지 않는다.
- 모든 주요 이미지는 회차의 `assets/`에 저장한다.
- 외부 이미지 URL을 직접 사용하지 않는다.

## 4. 직접 검수

발행 후보가 만들어지면 다음을 직접 확인한다.

### 원고

- Cover Story와 분야별 일반 기사 전체가 있는가
- 각 기사가 보도자료 정리에 머물지 않는가
- DEEP DIVE가 일반 기사를 반복하지 않는가
- LIFE SCENE이 개인 조언으로 끝나지 않는가
- EDITOR'S PICK이 기사별 요약이 아닌가
- 출처와 사실 상태가 정확한가

### 이미지

- 모든 이미지가 실제 래스터 생성 이미지인가
- 벡터풍·플랫·아이콘형 결과가 아닌가
- 얼굴·손·장비·문자 오류가 없는가
- 기사마다 다른 장면과 구도를 사용하는가
- 데스크톱과 모바일 크롭이 적절한가

### 지면

- 완성된 잡지로 보이는가
- 기사마다 시각적 리듬이 실제로 다른가
- 장식 모듈이 본문을 반복하지 않는가
- 1440px, 1366px, 1024px, 390px 화면에서 문제가 없는가
- 제1호보다 현저히 얇거나 단순해지지 않았는가

## 5. 보조 구조 검사

필요하면 다음 명령을 직접 실행한다.

```bash
python -m pip install -r requirements-tools.txt
python tools/validate_repository.py
```

검사기는 다음과 같은 기술적 실수를 찾는다.

- `issues.json`과 `archive/` 불일치
- `latest.json` 불일치
- 별도 CSS·JS·분할 HTML
- 런타임 기사 조립
- 외부 이미지 URL과 로컬 자산 누락
- 필수 섹션·이미지·앵커 누락
- 이미지 해상도·파일 크기·중복 문제

검사 통과는 발행 승인과 동일하지 않다. 검사기는 기사 깊이, 이미지 미감과 지면 완성도를 판단하지 못한다.

## 6. 사용자 검토

1. 완성 HTML과 주요 화면을 사용자에게 보여준다.
2. 사용자가 지적한 기사·이미지·지면 문제를 수정한다.
3. 명시적인 승인 전에는 `main`에 반영하지 않는다.
4. 승인 전에는 `issues.json`, `latest.json`, `archive/index.html`을 갱신하지 않는다.

## 7. 발행

사용자 승인 후 한 번에 다음을 반영한다.

1. 완성된 `archive/YYYY-MM-DD/`
2. `issues.json`
3. `latest.json`
4. `archive/index.html`
5. `ISSUE_HISTORY.md`

GitHub Pages는 `main` 브랜치 루트의 정적 파일을 그대로 사용한다. 별도 Actions 빌드·배포 과정은 없다.

## 8. 실패 처리

품질 검수에 실패하면:

- `main`에 반영하지 않는다.
- 공개 `archive/`에 실패본을 남기지 않는다.
- 작업 브랜치에서 원고·이미지·HTML을 다시 만든다.
- 기술적 조건만 맞추는 우회 수정은 하지 않는다.

외부 이미지가 준비되지 않았거나 실제 렌더링을 확인하지 못한 상태는 발행 불가다.
